
# 05 复盘

## 最难的问题

最难的是让 Agent 在资料冲突时保持可靠，而不是只检索到一条制度就直接回答。D01 写明报销期限为 30 天，D02 写明 15 天，资料没有提供适用范围或优先级。项目让模型决定继续读取两份原文，并在确认冲突后给出双方引用、说明缺口、请求澄清。程序同时校验引用必须来自已读取的原文，防止模型引用不存在的片段。

这也帮助我区分了“固定流程”和模型驱动的决策：代码负责执行工具、校验证据和限制步数；检索后读哪份资料、是否补充检索、何时追问或结束，由模型根据工具结果选择。资料替换实验中，两份制度变为一致后，模型的最终动作由追问变为回答，是比单条成功输出更有说服力的验证。

## 测试中发现的问题

离线测试通过并不代表真实模型稳定。复测时，DeepSeek 曾在 JSON 动作后输出额外文本，导致解析失败；另有一次 TLS 连接中断。项目随后显式关闭思考模式，并增加对首个有效 JSON 对象的解析和 Trace 警告。首个对象无效或网络不可用时，仍会返回明确的失败状态。这些失败及处理过程都保留在评估文档中。

检索也有边界：当前的字符片段匹配与少量同义词归一化，在 13 个自建问题中由基线 11/13 提升到 13/13，但样本很小，不能代表真实企业知识库的效果。资料外问题有时会进行多次无结果检索，说明还需要控制调用成本。

## 学习收获

我认识到，Agent 的效果不能只看最终答案。Trace 需要展示模型选择的动作、工具参数、返回摘要、后续动作和简短依据；引用还要能逐字定位到原文。真实模型运行、离线 Mock 测试和人工截图各自证明的内容不同，不能混为一谈。

冲突处理也不应只按版本日期选择“较新”的制度。若资料没有说明适用对象、生效关系或废止规则，可靠的结果应是披露冲突并请求确认。

## 未完成部分与下一步

本项目完成了试题要求的 CLI 核心链路，没有实现界面、线上部署或生产级权限管理。下一步我会优先：

1. 扩大改写问题和资料冲突测试集，记录检索召回与错误案例。
2. 为制度补充适用范围、生效状态和优先级字段，使冲突判断覆盖更复杂的情况。
3. 限制连续无结果检索和工具失败重试次数，降低调用成本。
4. 继续改进模型格式错误与网络故障的恢复，同时在 Trace 中保留恢复过程。

如果用于真实企业资料，还必须处理文档访问权限、版本更新、隐私保护和引用所支持的语义是否与回答一致。
